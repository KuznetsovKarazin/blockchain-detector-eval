# Compiler-only readiness stage: scope interpretation

The original `PROTOCOL_B.md` and `protocol_B_draft.json` remain unchanged. The protocol explicitly keeps external scoring/model fitting closed and requires a verified finite compiler inventory before tool execution. `validate_gate.py` defines only `begin-review` and `score` phases; it has no compiler-readiness phase. Its closed overall gate is not treated as permission for compiler execution.

A separately frozen compiler-only engineering preflight is consistent with completing input/tool readiness before the overall prospective freeze, provided its role is limited to the exact fixed identities and recorded compiler/import policy. This is a scope interpretation, not a claim that the original protocol expressly authorized this exact new runner. The existing user authorization to continue research engineering supports preparation; the root task additionally requires independent review and an explicit plan-bound root permit before actual corpus compilation. The prepared permit template is unapproved and cannot execute the runner.

The stage reads only public identity/hash manifests, the frozen compiler candidate list, verified tool inventory, pinned source bytes and its own configuration. It does not call the broader survey/setup gate, which also loads private source annotations and coordinator keys. It is annotation-file-blind, not perfectly blinded: source text itself can contain contextual comments. No labels, expert forms, sample strata, model outputs or score metrics enter this runner.

The fixed population remains 691 training plus 1,998 external files. All 39 files without compiler plans remain in the accounting. No compiler result may edit sources, change candidates, remove files, open the scientific scoring gate or choose a preferred model or source grouping. Every allowed candidate stays in its original order, with at most five attempts and 180 seconds per attempt. There are no diagnostic reruns in this version.

Output selection explicitly requests AST, ABI and unlinked bytecode with the optimizer disabled. The EVM target is each compiler's default, recorded as such; this is not reproduction of the original project's build configuration or deployment. Interface, abstract, empty-bytecode and unlinked-library outputs remain represented with explicit counts. Compiler success under this policy is distinct from Slither success and from semantic correctness.

The new context policy is deliberately explicit. Training imports use the exact pinned DAppSCAN `<audit-project>/<repo-snapshot>` source tree. Relative imports and exact direct source-unit paths can resolve only to hashed files inside that snapshot. No sibling snapshot, corpus-wide basename/suffix lookup, package fetch, inferred npm remapping or source rewrite is available. The external address-file corpus supplies no verified project root, so imports of other files are reported as missing context rather than attached to unrelated siblings. Missing/ambiguous/unpinned dependencies need a separately reviewed prospective context amendment, not silent runtime rescue.

Every compiler input is Standard JSON with literal `content` entries and no source URLs. Remote/absolute/escaped import literals, symlinks and path traversal are rejected during closure preparation. Execution copies only the verified closure into a fresh private workspace and supplies that workspace as the compiler's `--allow-paths`. Resource limits bound CPU/wall time, address space, open files and output collection. This is application-level import/argument restriction, not a kernel isolation claim: Landlock returned ENOSYS and local bubblewrap namespace probes were denied by this runtime. No fallback namespace or network-proxy bypass was performed.

Raw input JSON, compiler AST/bytecode and diagnostic text remain ignored private artifacts. Public outputs contain fixed identity pointers, hashes, bounded counts, normalized diagnostic categories, statuses, versions and timings. Neither unavailable files nor compiler failures are converted into negative vulnerability labels.

Primary documentation consulted for this engineering definition:

- [Solidity 0.4.19 compiler JSON interface](https://docs.soliditylang.org/en/v0.4.19/using-the-compiler.html): Standard JSON, explicit source contents, output selection and allowed filesystem paths.
- [Solidity import path resolution](https://docs.soliditylang.org/en/latest/path-resolution.html): source-unit namespaces, direct/relative imports and host filesystem callback behavior. Later-version documentation is not a claim that all historical compiler internals are identical; real results remain version-specific.
- [Linux Landlock documentation](https://docs.kernel.org/userspace-api/landlock.html): availability is queried explicitly; unavailable isolation is not silently reported as present.
